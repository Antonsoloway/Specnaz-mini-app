# Правила выпуска Royal CRM Mini App

## Обязательное правило истории изменений

Каждая новая версия Mini App выпускается только вместе с записью в разделе «История изменений».

Для версии `vX.Y.Z` одновременно должны быть выполнены все пункты:

1. Создан новый entrypoint `app-vXYZ.html` с номером новой версии.
2. Добавлена отдельная запись истории изменений для `vX.Y.Z` с кратким названием и фактическим списком изменений.
3. Новая запись истории стоит первой, предыдущие версии сохраняются без удаления.
4. Надпись «Текущая версия» и бейдж версии в приложении показывают один и тот же номер `vX.Y.Z`.
5. Новый entrypoint подключает файл истории этой же версии.
6. Старые entrypoint, если перенаправляют на актуальную версию, ОБЯЗАНЫ сохранять `location.hash` целиком. В hash Telegram передаёт launch-параметры (`tgWebAppData`), потеря hash ломает `Telegram.WebApp.initData` и авторизацию.
7. Для legacy-entrypoint запрещён `meta http-equiv="refresh"`: использовать только JS `location.replace()` с переносом `search` и `hash`, либо оставлять старый entrypoint самостоятельным.
8. Корневой `index.html` и постоянный `app.html` подчиняются тем же правилам сохранения Telegram launch hash.
9. Перед публикацией проверяется не только версия и история, но и авторизация из Telegram: `Telegram.WebApp.initData` не пустой.
10. Перед публикацией проверяется сценарий `Участники → профиль → Назад`, чтобы новая раскладка и достижения не исчезали после восстановления списка.
11. Интерфейсные статусы и достижения участников связываются с карточкой только по raw Telegram ID; имя/@ник не используются как идентификатор.
12. Правый блок статусов/достижений участника строится вертикально. Для участника проекта «МАЯК» порядок: `Админ` (если есть) → ранг → `МАЯК`. Плашка `МАЯК` всегда самая нижняя.
13. Каждая новая ачивка должна переживать повторный render и возврат `Назад`.
14. Плашка версии обязана открывать объект `window.RoyalChangelog` самой новой загруженной версии.
15. Постоянная Web App-точка входа — `app.html`. При каждом релизе меняется только её целевой `app-vXYZ.html`.
16. После успешной авторизации Mini App должен обеспечить право @doveofpeace_bot писать пользователю через `WebApp.requestWriteAccess()`.
17. `write_access_allowed` считается началом личного диалога с Голубем и приводит к приветственному сообщению.
18. Счётчики команды считаются из того же актуального состава, который реально выводится в карточке.
19. Если у команды нет фото, клиент не делает запрос изображения и показывает штатную заглушку.
20. Поиск должен быть быстрым и предсказуемым: без комбинаторных переборов, расстояний опечаток и тяжёлой обработки на каждой букве.
21. Каждый релиз проверяется минимум на Android и iPhone/iPad в Telegram WebView. На iOS отдельно проверяются `Назад`, карточки, участник → команда, @ник/ЛС, ранги, ачивки и внутренние кнопки.
22. Длинные списки имеют быстрые кнопки вверх/вниз, не перекрывающие нижнюю навигацию и не сбрасывающие поиск.
23. В шапке истории изменений блок `Помощь в разработке, тесты` содержит: `@sfinks_spb`, `@O_Chaplygina`, `@Yanochka_2404`. Внутри карточек отдельных версий этот блок не повторяется.
24. Поле поиска не заменяется/перерисовывается во время печати; фильтруются уже отрисованные карточки.
25. Запрещено блокировать `input`, `beforeinput`, `compositionstart`, `compositionupdate`, `compositionend` через `preventDefault()` или `stopImmediatePropagation()`.
26. Старые прямые обработчики поиска можно удалить однократным `cloneNode(true)` после первоначального рендера; дальше поле сохраняется до ухода со страницы.
27. На Android допускается лёгкое чтение `input.value` по таймеру только пока поле находится в фокусе, без вмешательства в IME.
28. Неоднозначные псевдорусские названия обрабатываются детерминированно; приложение не угадывает сотни вариантов и не считает расстояния опечаток.
29. В новом entrypoint загружается только один актуальный поисковый модуль.
30. Запрещён `prewarm` расширенного поискового индекса в основном потоке телефона.
31. На Android отдельно проверяются скорость открытия клавиатуры, свободный ввод, пробелы, стирание и поиск без скрытия клавиатуры.
32. Если карточки фильтруются через `hidden`, CSS обязан гарантировать их фактическое скрытие; визуальное число карточек совпадает со счётчиком.
33. Unified Snapshot Writer формирует для каждой команды и каждого участника массив `searchKeys` в `snapshot.json`.
34. `searchKeys` участника включают имя CRM, Telegram-имя, @username, команды, исходные названия команд, игровые ники, роли и игры. `searchKeys` команды включают официальное название, игры, транслитерации, псевдокириллическое чтение и подтверждённые алиасы.
35. Начиная с v0.5.49 `searchKeys` являются ДОПОЛНИТЕЛЬНЫМ слоем. Рабочая локальная логика поиска v0.5.47 сохраняется независимо и обязана работать даже при отсутствии, задержке или ошибке серверных ключей.
36. Серверные ключи не имеют права уменьшать множество результатов локального поиска. Итоговое совпадение = `локальный поиск v0.5.47 ИЛИ searchKeys`.
37. Подтверждённые контрольные алиасы: `Has ne dogonyat ↔ нас не догонят`, `XAOC ↔ хаос`, `TOPMO3OB HET ↔ тормозов нет`, `MOLOT POKA ↔ молот рока`, `HEPBbI B HOPME ↔ нервы в норме`, `HEPBbl B HOPME ↔ нервы в норме`, `Mbl Pycckue ↔ мы русские`, `CKAZKA ↔ сказка`, `BEHOM ↔ веном`, `Aquamarine ↔ аквамарин`, `Da budet swet 5 ↔ да будет свет`, `Mike ↔ майк`, `Xabib ↔ хабиб`, `JoyBand ↔ джойбанд`, `1BY ↔ 1бу`.
38. Псевдокириллическое чтение серверных ключей выполняется по словам. Для псевдорусского названия допускается ровно один детерминированный вариант чтения: визуально похожие латинские символы читаются как кириллица, остальные — обычной транслитерацией. Комбинации `bi`/`bl` могут читаться как `ы`. Это даёт, например, `CKAZKA → СКАЗКА`, `BEHOM → ВЕНОМ`, `Mbl Pycckue → МЫ РУССКИЕ` без перебора вариантов.
39. При изменении алгоритма серверных поисковых ключей увеличивается `searchIndexVersion`; изменение обязательно входит в `dataHash`, чтобы Unified Snapshot гарантированно перезаписался.
40. На страницах `Участники` и `Команды` непосредственно над поиском расположен фильтр игры `Все / РМ / РК`. Начальное значение — `Все`. Переключение фильтра не очищает введённый запрос.
41. Активный фильтр ограничивает и список, и область поиска. В режиме `РМ` командные поля/игровые ники/роли участника из Royal Kingdom не должны давать совпадение, и наоборот. Имя участника и @username доступны в каждой игре, в которой этот участник состоит.
42. Экранная клавиатура поиска закрывается при реальном движении пальцем по экрану, тапе вне поля поиска или Enter, при этом сам поисковый запрос сохраняется. Программный `scroll`/изменение viewport при открытии Android IME не должно автоматически снимать фокус.
43. В карточке каждой версии истории перечисляются только фактические нововведения, исправления и заметные изменения поведения. Повторяющиеся служебные фразы, кредиты, «сохранено без изменений» и аналогичный boilerplate в карточки релизов не добавляются.
44. Для подтверждённого псевдорусского названия, которое автоматический разбор прочитал неверно, добавляется точечный алиас. Такой алиас должен работать и в общем режиме, и при активном фильтре соответствующей игры.
45. Worker `/snapshot` обязан сохранять и передавать массивы `searchKeys` для участников и команд. Санитизация данных не имеет права удалять `searchKeys`; при изменении этого слоя проверяется наличие `snapshot.searchIndexVersion` на клиенте.
46. Кэш поискового haystack сбрасывается при смене объекта snapshot. Новые серверные ключи не должны требовать перезапуска приложения из-за ранее построенного кэша карточек.
47. Аватары участников и фото команд кэшируются на устройстве в IndexedDB. Ключ аватара строится по актуальному `avatarFileId`, ключ фото команды — по актуальному `photoUrl`; смена исходного изображения должна автоматически приводить к новому ключу.
48. Загрузка изображений работает cache-first: сначала проверяется постоянный локальный кэш, затем сеть. Отказ/недоступность IndexedDB не должна ломать изображения — используется обычная сетевая загрузка.
49. На слабом интернете запрещено массово скачивать все изображения одновременно. Аватары ставятся в очередь только при приближении к видимой области, одновременно выполняется не более двух сетевых загрузок.
50. Постоянный медиакэш автоматически очищает неиспользуемые записи старше 45 дней и ограничивается примерно 420 изображениями, чтобы не разрастаться бесконтрольно.
51. Собственная аватарка пользователя после первого восстановления из постоянного кэша не должна мигать буквенной заглушкой при повторных render текущего запуска. Уже показанный URL сохраняется в памяти и подставляется синхронно до следующего кадра.

## Текущая версия

На 18.08.2026 актуальная версия: `v0.5.56`.

Запись `v0.5.56 — Аватар без мигания` содержит:

- убрано краткое появление буквы-заглушки при повторной отрисовке своей карточки после загрузки snapshot;
- уже показанная собственная аватарка сохраняется в памяти текущего запуска;
- при пересоздании карточки этот URL подставляется синхронно, без `setTimeout` и без промежуточного кадра с буквой.

Все предыдущие версии сохраняются в истории изменений без удаления.
