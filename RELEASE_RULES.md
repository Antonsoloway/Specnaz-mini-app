# Правила выпуска Royal CRM Mini App

## Обязательное правило истории изменений

Каждая новая версия Mini App выпускается только вместе с записью в разделе «История изменений».

Для версии `vX.Y.Z` одновременно должны быть выполнены все пункты:

1. Создан новый entrypoint `app-vXYZ.html` с номером новой версии.
2. Добавлена отдельная запись истории изменений для `vX.Y.Z` с кратким названием и фактическим списком изменений.
3. Новая запись истории стоит первой, предыдущие версии сохраняются без удаления.
4. Надпись «Текущая версия» и бейдж версии в приложении показывают один и тот же номер `vX.Y.Z`.
5. Новый entrypoint подключает файл истории этой же версии.
6. Старые entrypoint, если перенаправляют на актуальную версию, ОБЯЗАНЫ сохранять `location.hash` целиком. В hash Telegram передаёт launch-параметры (`tgWebAppData`), потеря hash ломает `Telegram.WebApp.initData` и авторизацию.
7. Для legacy-entrypoint запрещён `meta http-equiv="refresh"`: использовать только JS `location.replace()` с переносом `search` и `hash`, либо оставлять старый entrypoint самостоятельным.
8. Корневой `index.html` и постоянный `app.html` подчиняются тем же правилам сохранения Telegram launch hash.
9. Перед публикацией проверяется не только версия и история, но и авторизация из Telegram: `Telegram.WebApp.initData` не пустой.
10. Перед публикацией проверяется сценарий `Участники → профиль → Назад`, чтобы новая раскладка и достижения не исчезали после восстановления списка.
11. Интерфейсные статусы и достижения участников связываются с карточкой только по raw Telegram ID; имя/@ник не используются как идентификатор.
12. Правый блок статусов/достижений участника строится вертикально. Для участника проекта «МАЯК» порядок: `Админ` (если есть) → ранг → `МАЯК`. Плашка `МАЯК` всегда самая нижняя.
13. Каждая новая ачивка должна переживать повторный render и возврат `Назад`.
14. Плашка версии обязана открывать объект `window.RoyalChangelog` самой новой загруженной версии.
15. Постоянная Web App-точка входа — `app.html`. При каждом релизе меняется только её целевой `app-vXYZ.html`.
16. После успешной авторизации Mini App должен обеспечить право @doveofpeace_bot писать пользователю через `WebApp.requestWriteAccess()`.
17. `write_access_allowed` считается началом личного диалога с Голубем и приводит к приветственному сообщению.
18. Счётчики команды считаются из того же актуального состава, который реально выводится в карточке.
19. Если у команды нет фото, клиент не делает запрос изображения и показывает штатную заглушку.
20. Поиск должен быть быстрым и предсказуемым: без комбинаторных переборов, расстояний опечаток и тяжёлой обработки на каждой букве.
21. Каждый релиз проверяется минимум на Android и iPhone/iPad в Telegram WebView. На iOS отдельно проверяются `Назад`, карточки, участник → команда, @ник/ЛС, ранги, ачивки и внутренние кнопки.
22. Длинные списки имеют быстрые кнопки вверх/вниз, не перекрывающие нижнюю навигацию и не сбрасывающие поиск.
23. В шапке истории изменений блок `Помощь в разработке, тесты` содержит: `@sfinks_spb`, `@O_Chaplygina`, `@Yanochka_2404`.
24. Поле поиска не заменяется/перерисовывается во время печати; фильтруются уже отрисованные карточки.
25. Запрещено блокировать `input`, `beforeinput`, `compositionstart`, `compositionupdate`, `compositionend` через `preventDefault()` или `stopImmediatePropagation()`.
26. Старые прямые обработчики поиска можно удалить однократным `cloneNode(true)` после первоначального рендера; дальше поле сохраняется до ухода со страницы.
27. На Android допускается лёгкое чтение `input.value` по таймеру только пока поле находится в фокусе, без вмешательства в IME.
28. Неоднозначные псевдорусские названия обрабатываются только через подтверждённые алиасы; приложение не угадывает сотни вариантов.
29. В новом entrypoint загружается только один актуальный поисковый модуль.
30. Запрещён `prewarm` расширенного поискового индекса в основном потоке телефона.
31. На Android отдельно проверяются скорость открытия клавиатуры, свободный ввод, пробелы, стирание и поиск без скрытия клавиатуры.
32. Если карточки фильтруются через `hidden`, CSS обязан гарантировать их фактическое скрытие; визуальное число карточек совпадает со счётчиком.
33. Начиная с v0.5.48 поисковая логика подготовки вариантов переносится на серверный Unified Snapshot Writer. Каждая команда и каждый участник получают массив `searchKeys` в `snapshot.json`.
34. `searchKeys` участника включают имя CRM, Telegram-имя, @username, команды, исходные названия команд, игровые ники, роли и игры. `searchKeys` команды включают официальное название, игры, транслитерации и подтверждённые алиасы.
35. Клиентский поиск v0.5.48+ не должен строить транслитерации, фонетические варианты или словари на телефоне. Во время ввода он только нормализует запрос и сравнивает его с готовыми `searchKeys`.
36. Подтверждённые контрольные алиасы серверного генератора: `Has ne dogonyat ↔ нас не догонят`, `XAOC ↔ хаос`, `TOPMO3OB HET ↔ тормозов нет`, `MOLOT ROKA ↔ молот рока`, `Aquamarine ↔ аквамарин`, `Da budet swet 5 ↔ да будет свет`, `Mike ↔ майк`, `Xabib ↔ хабиб`, `JoyBand ↔ джойбанд`, `1BY ↔ 1бу`.
37. При изменении алгоритма серверных поисковых ключей увеличивается `searchIndexVersion`; изменение должно попадать в `dataHash`, чтобы Unified Snapshot гарантированно перезаписался.

## Текущая версия

На 17.08.2026 актуальная версия: `v0.5.48`.

Запись `v0.5.48 — Поисковые ключи из CRM` содержит:

- Unified Snapshot Writer обновлён до `v1.1.0`, schema `1.4.0`, `searchIndexVersion 1.0.0`;
- каждому участнику и каждой команде добавляется массив готовых `searchKeys`;
- подтверждённые сложные названия и алиасы готовятся на сервере;
- Mini App больше не строит сложные варианты поиска на телефоне, а выполняет только сравнение по готовым ключам;
- Android-safe поле поиска и CSS-скрытие результатов сохранены;
- блок помощи в разработке и тестировании сохраняет `@sfinks_spb`, `@O_Chaplygina`, `@Yanochka_2404`.

Все предыдущие версии сохраняются в истории изменений без удаления.
