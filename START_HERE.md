# Royal CRM / «Таблица ЧП» — START HERE

> **Обязательная инструкция для любого нового ChatGPT-чата или нового разработчика.**
> Не начинать работу по памяти предыдущего диалога. Сначала восстановить фактическое состояние проекта по источникам ниже.

## 1. Порядок чтения перед любой новой работой

Читать строго в таком порядке:

1. `CURRENT_STATE.md` — текущая база состояния проекта.
2. Последние записи в `WORK_HISTORY.md` — что было сделано недавно, что проверено, что откатывалось.
3. `RELEASE_RULES.md` — обязательные инварианты релизов Mini App.
4. Если задача относится к таблицам — `docs/tables/ADMIN_TABLE_STRUCTURE.md` и `docs/tables/PUBLIC_TABLE_STRUCTURE.md`.
5. Если задача относится к Apps Script таблиц — читать **фактическое зеркало живого проекта** в `apps-script-live/`, а не старую копию по памяти.
6. Если задача относится к Mini App frontend — открыть текущий `app.html`, актуальный `app-vXYZ.html` и только те JS/CSS-модули, которые реально подключены этим entrypoint.
7. Если задача относится к Worker — открыть `worker/wrangler.toml` и текущий `worker/src/entry-*.js`, на который указывает `main`.
8. Если задача зависит от данных — проверить актуальный `Antonsoloway/royal-crm-data/snapshot.json` и/или живую Google Sheets, а не делать вывод по старому снимку.

## 2. Иерархия источников истины

При расхождении источников использовать такой приоритет:

1. **Фактический production/runtime**, если его можно проверить.
2. **Живые Google Sheets / живой Apps Script**, если задача относится к таблицам.
3. **Текущие файлы GitHub `main`**, если задача относится к frontend/Worker/репозиторию.
4. `CURRENT_STATE.md`.
5. `WORK_HISTORY.md`.
6. История старых чатов и память ChatGPT — только дополнительный контекст, никогда не единственный источник кода.

Если документация расходится с кодом или runtime, сначала установить фактическое состояние, затем **обязательно исправить документацию**.

## 3. Правило перед изменением

Перед любой правкой:

- открыть реальный файл;
- проверить его текущую версию/SHA и связанные модули;
- понять, что реально задеплоено, а что только лежит в репозитории;
- проверить зависимости и ранее принятые инварианты;
- не повторять уже откатанное или отклонённое решение без отдельной причины.

Для существующего GitHub-файла: `fetch_file` → `update_file` с актуальным SHA.

Для Apps Script: сначала сверка с `apps-script-live/`; если требуется менять live Apps Script, после правок соблюдать `clasp status` перед `clasp push` и указывать пользователю **ФАЙЛ → ФУНКЦИЯ → ОЖИДАЕМЫЙ РЕЗУЛЬТАТ**.

## 4. Обязательное завершение каждой законченной работы

После того как изменение принято/проверено пользователем, новый чат обязан обновить проектную базу знаний:

1. **`CURRENT_STATE.md`** — обновить текущую версию, активные файлы, deployment/runtime, новые инварианты, известные проблемы и фактическое состояние.
2. **`WORK_HISTORY.md`** — добавить запись о выполненной работе: дата, задача, причина, изменённые файлы, результат проверки, deployment status, важные решения/откаты.
3. **`RELEASE_RULES.md`** — обновлять, если появилось новое постоянное правило или изменился старый инвариант.
4. **Changelog Mini App** — для каждого frontend-релиза добавить только фактические нововведения/исправления.
5. **`docs/tables/*.md`** — обновлять, если изменена структура листов/колонок/служебных связей таблиц.
6. **`apps-script-live/`** — после фактического изменения и push Apps Script заново синхронизировать live-проект через `scripts/sync-live-apps-script-to-github.sh`, чтобы GitHub снова соответствовал production Apps Script.
7. Если изменён `snapshot.json`-контракт — зафиксировать schema/searchIndex/unified writer версии в `CURRENT_STATE.md`.
8. Если изменён Worker — зафиксировать repo main/version и отдельно отметить, подтверждён ли production deploy.

**Работа не считается полностью завершённой, пока состояние и история не обновлены.**

## 5. Что писать в WORK_HISTORY

Минимальная запись:

- дата и время;
- задача пользователя;
- найденная причина/диагноз;
- что именно изменено;
- файлы/версии/коммиты;
- что проверено;
- что не проверено или требует ручной проверки;
- если был неудачный подход/откат — кратко зафиксировать его, чтобы следующий чат не повторил.

Не записывать токены, секреты, приватные ключи, содержимое `.clasp.json` или Script Properties.

## 6. Apps Script — live mirror

Полное зеркало текущего standalone Apps Script лежит в:

`apps-script-live/`

Оно получено через `clasp pull` из `~/table-chp-1.3`.

`apps-script-live/LIVE_MIRROR_MANIFEST.md` содержит SHA-256 всех сохранённых файлов.

`.clasp.json`, токены и Script Properties намеренно не хранятся в GitHub.

Для повторной синхронизации:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Antonsoloway/Specnaz-mini-app/main/scripts/sync-live-apps-script-to-github.sh)
```

Скрипт сначала делает backup, выполняет `clasp status`, `clasp pull`, проверяет критические файлы и только затем отправляет зеркало в GitHub.

## 7. Точная формулировка для начала нового чата

Можно написать всего одну фразу:

> **Продолжаем Royal CRM / «Таблица ЧП». Сначала прочитай `START_HERE.md`, `CURRENT_STATE.md` и последние записи `WORK_HISTORY.md`. Затем сверься с фактическим кодом и данными, относящимися к задаче. GitHub/живой runtime — источник истины. После выполненной работы обязательно обнови `CURRENT_STATE.md` и `WORK_HISTORY.md`.**

Этого достаточно; длинный handoff вручную не нужен.
