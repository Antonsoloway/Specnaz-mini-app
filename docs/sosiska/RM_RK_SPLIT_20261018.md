# Сосиска: отдельные Royal Match и Royal Kingdom (18.10.2026)

## Решение

Один административный модуль получает две независимые страницы: **Сосиска RM** и **Сосиска RK**. Каждая страница использует одинаковую структуру интерфейса (поиск по названию/рейтингу, фильтры, карточка и состав, отслеживание, снимки/журнал/дельты, вся история, сравнение, графики, экспорт, ИИ-анализ, турнирная/боевая таблица там, где есть источник). При переключении очищаются экранные данные и незавершённые запросы; ID, история и результаты разных игр никогда не смешиваются.

**RM сохраняет существующий production-контракт:** если `game` не указан, все запросы идут в прежний RM-agent. Для уже работающего RM не создаются новые снимки, не меняется расписание и не переписывается история. В CRM-пикере выбора команды по ID также остаётся RM по умолчанию.

**RK использует отдельно:**
- выделенный read-only поисковый Worker `specnaz-royal-kingdom-search-stage1`, build 33931. Он умеет нативные searchTeams, getTeamInfo, getProfile, health и гибридный поиск (по имени, псевдокириллице, рейтингам и фильтрам).
- выделенный аккаунт `aia` и Worker `specnaz-royal-kingdom-events-stage2` для `getTeamClash`: командные очки группы, свои известные личные очки, без выдумывания очков остальных команд.
- новый Durable Object `SosiskaKingdomMonitor`, ключ `kingdom-monitor-v1`: отдельное облачное расписание с интервалом 60–10080 минут, до 100 наблюдаемых команд, snapshots по одному teamId, история и дельты членства, активности и доступных событий. Компьютер для периодического чтения не требуется после настройки Cloudflare.
- новый `SosiskaKingdomAnalysisJobs`, отдельная SQLite DO и отдельное имя задачи: переиспользует конвейер ИИ со своими RK snapshot/history. В prompt явно сказано, что RK `Crown` в UI-адаптере = родной `Cup`, а не короны RM. 
- Подписанный экспорт по `game='rk'` читает только RK DO; старый экспорт RM остаётся совместимым с legacy-токенами.

## Условия точности

В интерфейсе RK нативные **кубки** подписаны кубками, командные очки берутся из поля `Score`, а не суммой уровней. Внутри только общего UI-аналитического адаптера `Cup` хранится ещё и в поле `Crown`; `metricAliases` документирует отображение. В RM это поле по-прежнему означает реальные короны. Отсутствующие профили и личные очки в RK остаются недоступными, не равны нулю. Расписание чередования RM не применяется к RK. Командные битвы RK показываются по `groupId/eventId`, личные результаты чужих команд не заявляются.

Слой доступа /admin-agent остаётся **только для проверенных Telegram-администраторов**, ни RK-сессионные токены, ни API-ключи не попадают в JS/экспорт. Два серверных секрета для фасада должны быть созданы в аккаунте Worker ЧП:
- `RK_AGENT_API_KEY` из отдельного существующего RK search Worker,
- `RK_EVENT_API_KEY` из существующего RK events Worker.
Существующие `RM_AGENT_API_KEY` и `RM_EVENT_API_KEY` не заменяются. Новый monitoring/analysis DO требует применения миграции Wrangler в аккаунте Worker ЧП.

## Верификация / состояние доставки

17–18 октября подготовлен исходный код отдельно от production и добавлены RK-тесты на обработку входных данных, админскую границу, групповую таблицу, невозможность узнать личные баллы чужой команды, данные снимков и изоляцию RM/RK. Профильные тесты Сосиски: **137 PASS, 0 FAIL**. В UI дополнительно проверены RM/RK вкладки и очистка поиска при переключении.

Попытка получить свежие живые данные RK с рабочего компьютера через отдельный Worker закончилась сетевым `WinError 10060` (тайм-аут); поэтому живая приемка через Telegram и Cloudflare Worker ЧП **не подтверждена**. Доступный Wrangler OAuth подключён к аккаунту `62c513d37c8b15db448b263dfb7d2dee` (RK), а production miniapp Worker находится в другом аккаунте `0dd3beb421783a043d0327ac771a3f1a`. До получения авторизации к последнему запрещается заявлять опубликованный RK UI. Главная ветка/production не меняются до CI PASS и проверки правильного аккаунта, секретов и Telegram acceptance.

Полный глобальный запуск `tests/*.test.mjs` нашёл ошибки в независимом тесте `golub-ingress-resilience.test.mjs`; к Sosiska source они не относятся. Это **не** зелёный общий CI, проверять PR workflow отдельно.

## После входа в аккаунт Cloudflare мини-приложения

1. Настроить оба RK secret в Worker ЧП, не передавая содержимое в GitHub.
2. Убедиться, что Workers Builds поддерживает две новые SQLite DO migrations; проверить `wrangler deploy --dry-run` и CI.
3. Подготовить UI release согласно `RELEASE_RULES.md`: новый entrypoint и запись в истории изменений, версия и redirect без потери Telegram launch hash. 
4. Пройти live приемку на Android/iOS Telegram: переход RM↔RK, RK поиск, открытие команды, включение и остановка слежения, снимки, полный период, графики, таблица боёв, экспорт, анализ, отсутствие смешивания игр, админские права.
5. После PASS переключить production и зафиксировать commit/Worker version, не трогая рабочие RM watches.
